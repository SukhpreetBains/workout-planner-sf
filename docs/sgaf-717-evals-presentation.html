SGAF-717 · Evaluating Ascent skills and agents

Three questions, not one.

Did it do the job right. What did it cost, and was that predictable. How much time did it save. Every slide after this one answers one of the three, in that order.

1

Did it do the job right?

Not “the script ran without an error.” Does the document hold up against one a delivery lead has already approved.

2

What did it cost, and was that predictable?

Tokens and dollars for one run, and how far that number moves when you run the same job again. The spread matters as much as the average.

3

How much time did it save?

The agent’s clock against a human baseline that a human recorded, reported where the work is tracked.

Correctness alone is not a product claim. You can get a usable answer out of Claude directly after a few hours of prodding and several million tokens. What this library sells is that the answer lands in the same place every time, at a price we can quote.

01 · What we are evaluating

Point at the right places once. Get a short briefing for each later job.

The user

“What should this agent know about this project?”

Someone opens an unfamiliar project folder and points at the files, folders, chats and document locations that matter.

→
Step one · discover-project-context

Build a project map

Records each trusted location, what it is for, and whether we can actually read it. No document bodies, no chat history.

→
Step two · retrieve-project-context

Return a briefing for one job

For “prepare the Risk Gate 1 brief,” it returns the relevant evidence, links back to each source, and names anything out of reach.

The briefing in the third box is the thing the three questions get asked about. It is the only output of this workflow that another skill, or a person, ever has to trust.

02 · The project map

The map records where information lives. It does not copy the information.

// What the map records project: { name, current goal, key terms } locations: { local folders, chats, documents } purpose: [ why each location matters ] access: [ available, unavailable, unknown ] // What it never records document bodies: "not copied" chat history: "not copied" credentials: "never copied" access errors: "short explanation only"
// One entry, and one gap location: "Client Docs / Mobilize" why it matters: "scope and readiness evidence" can we read it?: "yes" location: "project email threads" can we read it?: "no — recorded as an access gap"

A source we cannot read stays on the map with the reason. The later skill reports the gap instead of searching somewhere broader to cover for it.

03 · The briefing

A short answer, with its evidence attached and its gaps named.

The requestWhat comes backWhat it says about what it could not reach
“Prepare a Risk Gate 1 brief for Mobilize.”A short overview, the selected evidence, a link to each source, and the date the information was collected.“The project email threads are unavailable, so this brief does not include them.”
“What has changed in the readiness plan?”The relevant decisions and changes with the excerpt behind each one, or the saved answer if it is still current.“The available sources do not answer this. Here is the source that needs access.”
In the briefing

Enough to start useful work

A direct answer, the excerpt behind every claim, a link to each source, the date it was collected, and the gaps.

Not in the briefing

Everything the next step does not need

No folder exports, no unrelated documents, no credentials, and no content from a source we were not given access to.

Question 1 grades this. The artifact that got handed over — not the sequence of steps taken to build it.

04 · Question 1 — what we check today

Four checks. Every one of them is about the script behaving.

Where things are
The map lists each known location with what it is for, and keeps the unreadable email source marked as a gap.
Fails if a document body or a credential ends up in the map.
Out of reach stays out of reach
Readable evidence comes back; the email content does not.
Fails if retrieval goes looking outside the recorded sources to compensate.
The briefing stays small
The scope, governance and readiness evidence is selected, and the briefing stays inside its size limit.
Fails if it returns a folder dump instead of a selection.
Old answers are not passed off as current
A saved answer that still matches the job is reused; a stale or unrelated one is rejected.
Fails if a stale answer is presented as if it were current.

All four have to pass. One failure fails the change. But four passing checks prove the scripts behaved — not that the briefing was any good. Nobody outside the team ever reads a project map.

05 · Question 1 — the known-good document designed, not yet run

Compare the output against a document a human already got right.

How it works
  • Take a finished deliverable from a past engagement — a RAID log, a Risk Gate brief — one a delivery lead approved and cleared for evaluation use.
  • Run the workflow from the same inputs.
  • Compare it section by section: which required sections are present, which are missing, and whether any claim in ours is unsupported by the evidence it cites.
What it producesA verdict of pass, partial or fail, with the missing sections named. A partial is useful: it says exactly which section the workflow does not know how to produce yet.
# ILLUSTRATIVE SHAPE — no comparison has been run reference: "Mobilize RAID log, 2025" required sections present: 8 of 9 missing: [ "Escalation path" ] claims with no supporting evidence: 0 verdict: "partial"

The reference documents are not in the repository yet, and nothing on this slide has been measured. What is settled is the standard: a human-approved artifact decides whether ours is right.

06 · Question 2 — cost, and how much it moves

A cheap average with a wide spread is a worse product than a dearer run that lands in the same place.

The same job, five times  illustrative41k · 44k · 43k · 70k · 45kMiddle run 44,000 tokens. The cost jumps around by about 25 percent (coefficient of variation 0.25). Verdict: variable — budget with headroom, and find out what the fourth run did differently.
What one run records
  • Input and output tokens, with cache reads counted and priced separately.
  • Dollars, from one rate file with the date the rates were checked.
  • Turns and tool calls.
How much the cost jumps aroundVerdictWhat it means for a client conversation
Under 10%predictableA per-run cost is safe to quote.
10% to 30%variableBudget with headroom, and investigate the spread.
Over 30%unpredictableDo not quote a per-run cost. The workflow is not stable.

“Is it 70 credits one time and 40 credits another time?”Calvin O’Keefe, 21 August. Thresholds above are a provisional starting position, recorded so they can be argued with.

First real measurement, 21 August. Three real development sessions, read out of the session logs by the new harness: spread 0.86 — unpredictable, nearly three times the top band. These were ad-hoc working sessions, not controlled eval runs, so this is not a fair measure of a skill workflow. It is the first real evidence on the question above, and it does not point the way we would like.

07 · Question 3 — time saved

The agent’s clock is the easy half. The baseline has to come from a human.

Agent, measured  illustrative2m 36sFirst to last timestamp in the session log, read by code.
Human baseline  illustrative4h 00mDelivery-lead estimate, 21 August, for the Mobilize RAID log. Recorded with who said it and when.
Difference  illustrative3h 57mThe only figure worth putting in front of a client, and only with its baseline attached.
The rule

No baseline, no claim

A baseline is recorded with who gave it, when, and for which deliverable — or the field stays empty and the run reports no time saved. It is never derived from the agent’s own run.

Where a baseline comes from

The person who did it by hand

The delivery lead or consultant who produced the same deliverable last time, asked once per deliverable type. One recorded estimate covers every future run of that job.

A number the agent produces about its own value is not evidence. This is the one field in the whole harness that a human has to fill in.

“In the resolution of the Jira story or in the pull request that the agent makes, it puts in some metric around hours saved versus doing it manually. Instead of it just being some vague, like, oh, it feels like it took an 8 point story to a 5 point story.”Calvin O’Keefe, 21 August

Two rules for the block

Facts only, and nobody types it

No adjectives, no verdict on whether the run went well. The harness writes it from the run record, so the figures in the story and the figures in the log cannot drift apart.

10 · Who runs it, and when

Both, staged. We run it now to catch drift. It ships with the library later.

Now · decidedInternal drift detectionWe own the skill library. The suite runs whenever a skill, template or prompt changes, and it fails the change if correctness drops or the cost spread widens.
Later · decidedExternal self-validationOnce the library ships beyond the team, the same suite goes with it. Anyone who modifies a skill can prove their change still produces a passing, affordably priced output.
What that forces on the design now

Build it for the second audience

No dependency on a local checkout, no private client material in a fixture, and no paths that only exist on one person’s machine. Retrofitting that later is a rewrite.

11 · What this suite cannot tell you yet

This suite tests plumbing. The real test arrives with the skills that produce documents.

What is under test today

Two deterministic shell scripts

They produce a map and a briefing. Both are internal plumbing. Nobody outside the team reads either one.

So the evaluation is thin

There is not much to measure

No client-facing document to compare against a known-good one, no model varying between runs, and a cost close to nothing. More checks would not change that.

And the checks are guesses

Written from the design, not from failures

The four checks came from reading the skill contract. They are real invariants and worth gating on, but we have not yet watched this workflow fail for real.

The next skills turn transcripts, chats and spreadsheets into structured documents and microsites. Those have a deliverable someone signs off on, a model in the loop, and a real bill — which is where all three questions finally have something to measure. That is the reason for the order on the next slide.

12 · What we build next

Five moves, in the order the three questions need them.

Done
Four deterministic checks on the project-context scripts.
Gate: all four pass on every change to the scripts.
Now · question 2 and 3
Telemetry. Tokens, dollars and wall clock read out of the session logs by code — never by a model re-reading a transcript.
Gate: every run writes cost and time; five runs of the same job produce a spread and a consistency verdict.
Next · makes them claims
The comparison arm, and one recorded human baseline per deliverable type.
Gate: every headline number is a difference against the same job run without the library, and no time-saved figure ships without a dated human source.
Then · before more checks
Error analysis. Read real traces, note what actually went wrong on each, group the notes and count them.
Gate: a failure list with frequencies, replacing the one we guessed from the design.
Then · question 1, properly
Golden documents: one approved reference artifact per deliverable type, compared section by section.
Gate: present, missing and unsupported counted per section, with a pass, partial or fail verdict.
Then · what code cannot check
A model judging one thing at a time — is every claim supported by the evidence it cites — and the judge itself checked against a person’s labels first.
Gate: one yes-or-no question per judge, and measured agreement with the named expert before it gates anything.

Error analysis sits before the golden documents on purpose. Writing more tests before reading real traces is how the first suite ended up correct and useless.

Translations. pass@k: one good attempt is enough. pass^k: every attempt has to hold. Coefficient of variation: how much the cost jumps around. contract-enumeration: we guessed these failures from the design and have not yet watched it fail for real.

Appendix B · the four checks in contract form

Task IDs, intents and assertion classes.

Task IDIntentGraded surfaceAssertion classesPasses when
context-discovery-metadatashould-dooutcome + trajectorystate-verification, schema-validation, forbidden-contentThree canonical locations are recorded with bounded discovery measurement, the unavailable email source keeps its access state, and no source body reaches the map or brief.
context-unavailable-sourcemust-notoutcome + trajectoryforbidden-content, tool-call-verification, state-verificationAccessible evidence returns and the email gap persists, while the restricted body never appears and retrieval never widens past recorded sources.
context-bounded-retrievalshould-dooutcomerelevance-selection, bounds-check, forbidden-contentRequired scope, governance and readiness evidence is selected within the per-source and total size limits.
context-cache-boundarymust-notoutcomefreshness-check, relevance-selection, state-verificationA fresh, task-matching cache is reusable, while a stale one and an unrelated one are both rejected.

A must-not case is a guardrail, not a test we expect to fail. It passes when the forbidden thing does not happen. Naming the assertion class is what makes coverage checkable: a suite with no forbidden-content assertion is not testing leakage, whatever its pass rate says.

Error analysis, when we get there: collect real traces, write a free-text note on each (open coding), group the notes into categories (axial coding), then let the frequency counts decide what to evaluate next. One named domain expert is the final authority on pass and fail, rather than an average of reviewer opinion. The same loop is already implemented for Agentforce conversations in the agentforce-error-analysis, agentforce-review-interface and agentforce-validate-judge skills.

The classification axes

The method that produces the tests

Error analysis first. Open coding, axial coding and the failure taxonomy. Binary over Likert. A model judge as one scoped yes-or-no classifier, validated against expert labels. Offline suite versus production monitoring versus inline guardrail. One named arbiter of quality.
