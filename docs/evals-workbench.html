Question 2

What did it cost, and was that predictable?

An average with a wide spread is a worse product than a slightly dearer run that lands in the same place every time. So the spread is shown, not just the middle.

With the skills against plain Claude

The same task, same host, same model, run twice: once with the Ascent skill library available and once without it. The reportable result is the difference, not either absolute.

Question 3

How much time did it save?

Agent wall-clock against a recorded human baseline for the same deliverable. A baseline is a figure a person gave us. It is never derived from the agent's own run, and a missing baseline is shown as missing rather than as zero.

    Appendix

    The words on this page

    Plain reading first. The standard term is in small type, once, for anyone who needs to map this suite onto the wider evaluation literature.

    • Did it do the job right - the deterministic checks all held, and where a known-good human document exists, the output was compared against it section by section. correctness · outcome verification
    • One good attempt is enough - the workflow is allowed several tries and we score the best one. Right for a deliverable a person will review anyway. pass@k
    • Every attempt has to hold - the correct estimator for a guardrail. One leak in five tries is a failure, not an eighty per cent pass. pass^k
    • How much the cost jumps around - the spread of tokens per run divided by the average, so a cheap-but-erratic workflow cannot hide behind its mean. coefficient of variation
    • We guessed these failures from the design; we have not yet watched it fail for real - the tested failures were read off the skill contract rather than found in real traces. They are real invariants, but they are not evidence of what goes wrong in practice. contract-enumeration provenance
    • Checked by code, not judged by a model - every assertion here is a Python check with a deterministic answer. Nothing on this page grades tone, completeness or groundedness. code-based grader
    • Protects behaviour that already works - as opposed to a suite aimed at new or hard behaviour, which is expected to have failures in it. regression · capability
    • Grades the finished artifacts, and the steps taken to make them - this suite checks the files produced and the boundaries respected while producing them. outcome verification · trajectory analysis
    • One run, no repetition - deterministic scripts give the same answer every time, so a single trial is enough. A model-driven suite would need repeated trials before any consistency claim. single-trial

    This suite's classification

    Read straight from eval-plan.json. Kept for anyone auditing coverage; it is not the headline.

    Honest limitation The project-context skills are deterministic shell and Python scripts with no client-facing deliverable, so their evaluation is thin by nature. Cost, consistency and time-saved figures become real with the skills that turn unstructured content into structured documents. That is the argument for staging the work, not something to bury.
