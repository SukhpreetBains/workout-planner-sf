What this repo is

An AI-assisted discovery engine that turns raw client materials into a defensible backlog.

This is a Codex-first knowledge hub + skill library. You drop discovery documents in, run guided agent workflows, and out comes a traceable, prioritized set of user stories the solutions team can build against — with narrative and evidence backing every item.

The 5-stage pipeline

Each stage produces the input for the next. You talk to the agent in plain English; it selects the matching skill and runs it against the knowledge hub.

STAGE 1 · once per project
/setup
Onboard the repo, organize the inbox, and extract canonical entities from every discovery doc into the 4 Excel registers.
→ 100–200+ records
→
STAGE 2
/synthesize
Turn structured register data into a readable current-state narrative organized by theme, function, or system.
→ 02 - Current State/
→
STAGE 3
/analyze
Answer structured questions — themes, gaps, priority bands, traceability — as a durable AnalysisCore + views.
→ AnalysisCore JSON
→
STAGE 4
/manage-backlog
Seed the backlog workbook with epics → features → user stories, traced back to source pain points.
→ Backlog Tracker.xlsx
→
STAGE 5
/compose-deliverable
Package client-facing deliverables (decks, workbooks, briefs) from approved templates.
→ .pptx / .xlsx / .md
Between capture and the pipeline: new knowledge flows through /review. Processing queues proposals; you accept / reject / edit them; /review --apply writes accepted items to the registers. Nothing lands in the authoritative registers without review.

The mental model

Knowledge Hub

Your project's content

Everything client-facing and durable: inbox, sessions, registers, current/future state, backlog, reference materials. This is what you read and share.

The .agents system

The operating machine

Skills, the Python engine, references, overlays, and prompts. It reads and writes the hub but stays out of the way. Rarely edited by hand.

Registers as truth

4 Excel workbooks

Current State, Future State, RAID+, and Stakeholders are the single source of truth. Everything downstream derives from them.

How the machine actually works

Under the hood: registers, the review loop, skills, overlays, and the engine.

The repo separates durable truth (the 4 registers), derived state (mirrors, search index, graph), and orchestration (skills + the Python engine). Understanding those three layers explains almost everything.

The four authoritative registers

RegisterHoldsWritten byRead by

Future_State.xlsxObjectives, focus areas, solution directions/setup, /review --applyanalyze, manage-backlog, compose

Register writes are governed: they only happen through write_registers.py under the write contract (.agents/references/register-write-contract.md). Direct hand-edits are discouraged because they bypass identity resolution, enum normalization, and the derived-state refresh.

Anatomy of a skill

SKILL.md

The playbook the agent reads: when to use it, the step-by-step procedure, and which references to load. Registered in skills-catalog.yaml.

references/

Deep, load-on-demand docs — modes, patterns, schemas, sub-agent prompts. Kept out of the main file to stay context-light.

scripts/

Bundled Python helpers (excel, docx, pdf, pptx, analyze). Runtime copies live under .agents/runtime/skills/.

Overlays — how specialties plug in

  • Capability overlays (salesforce, clm): activated during setup; add backlog profiles, scaffolding actions, AGENTS.md blocks, and sometimes extra skills (e.g. hubbl-query).
  • Industry overlays (manufacturing): layer domain guidance and follow-up fields on top of a capability.
  • Registered in .agents/overlays/registry.yaml; the active choice is recorded in the project state and backlog profile.

The Python engine (.agents/scripts)

Skills orchestrate; these scripts do the deterministic heavy lifting. Everything runs through the py / py.cmd launcher so the runtime is consistent.

Intake & writes
  • intake_engine.py — evidence-first observation extraction
  • intake_review.py — proposal review/apply mechanics
  • write_registers.py — governed register writes
  • identity_resolution.py — dedupe/merge entities
Derived state & query
  • refresh_derived_state.py — rebuild all derived artifacts
  • build_graph.py — relationship graph
  • refresh_search_index.py — searchable index
  • query.py — retrieval across the hub
