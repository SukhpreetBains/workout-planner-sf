SharePoint Workspace Migration Plan

enterprise-accelerated-delivery → ascent skill library + shared SharePoint architecture

Migrating the concepts of enterprise-accelerated-delivery (EAD) into the ascent skill library and a shared SharePoint folder architecture. Summit is the delivery methodology, so phase names and order come from the Summit MCP: Mobilize, Discover, Deliver, Transition, Enhance & Operate, Close.

01

Three layers, cleanly separated

One design rule governs everything below. Anything that costs tokens produces a file in the folder; anything derived from the folder is free to rebuild and lives outside it.

Layer 01
ascent git repo
Reusable skills, references, templates, and scripts.
skills templates scripts no live project content
Layer 02 · source of truth
SharePoint Opportunity folder
OneDrive-synced engagement workspace. The only shared source of truth: human-facing content plus a small amount of machine-managed state.
human content managed state no code no databases no per-user caches
Layer 03
Per-machine local caches
Deterministic, token-free, rebuildable projections of the workspace: search index and graph.
rebuildable token-free never synced
Governing rule. The SharePoint folder is the source of truth; every local cache is a deterministic, token-free function of its contents.

03

Agent permission guardrail (v2)

Written to the Opportunity root AGENTS.md by initial-setup from a static template. Applies to every agent session on every host.

LocationPermissionWhat that means in practice
Agent Inbox/ Full read-write All iteration and work-in-progress happens here.
Content Inbox/Threads/ Create only Add exports; never modify, move, or delete existing files.
Content Inbox/Transcripts/
Content Inbox/Client Docs/		 Read only Sources are evidence. They are never edited or relocated.
Deliverables/ Create only Only files whose name ends in _AGENT_DRAFT before the extension. Never edit, rename, move, or delete anything, including a draft the agent created earlier.
Config/ Gated write Agent-writable, but every create or update is gated behind explicit human approval in the current conversation. No silent writes.
The filesystem is the workflow engine. Nothing becomes approved truth unless a human moves or renames it into place.

05

Trackers and the entity ID scheme

Structured project data lives as markdown/YAML trackers inside the Deliverables phase folders. Excel views are generated on demand as deliverables, never the source of truth — EAD's whole-file xlsx rewrite model conflicts fatally with SharePoint co-authoring and sync.

STK-

Locked from day one. Every tracker entry has a stable id and typed link fields referencing other IDs, for example addresses: [OBJ-003]. IDs are permanent anchors for citations and the substrate the Phase 2 graph is built on. Retrofitting IDs is not practical, so the scheme is carried over from EAD verbatim.

Three EAD ideas are preserved as skill instructions plus light validation — not machinery.

01 · Closed action set

Every extracted item is exactly one of: new entity, update to existing entity, contradiction, evidence attachment. Anything else is out of contract.

02 · Citation discipline

Every fact carries source file plus location — timestamp for transcripts, permalink for threads, page or section for documents — anchored to entity IDs.

03 · Idempotence via the log

Content-hash keyed. Any future session, on any machine, can tell what has been handled. Files are never moved out of Content Inbox: the guardrail forbids it, and provenance is better this way.

07

Retrieval and caches

Phase 1 ships no cache at all. Agents read trackers and relevant sources directly, because early-engagement corpora fit in context, and retrieve-project-context covers import-time ranking and bounded summaries.

Phase 1 · none

Direct reading. No index, no graph, no manifest. One Phase 2 stub ships now: the scheduled import run calls the indexer if present and no-ops otherwise, so adding the index later requires no change to the scheduled job.

Phase 2 · per-machine cache

Built entirely by script. Zero tokens, seconds to rebuild. Lives at ~/.ascent/<account>/<opportunity>/ and is never synced.

Why this cannot corrupt truth
  • No cache writes back to truth.
  • Two users' caches differ only by sync lag or build lag, both detectable via manifest-versus-folder hash comparison in the status command.
  • Divergence self-heals via rebuild.
Hard constraints
  • Freshness is content-hash based, sharing the processing log's scheme. mtime is never trusted: OneDrive rewrites it.
  • SQLite never lives on, and is never opened from, a synced path.
  • No shared cache on SharePoint. Every machine builds its own.

10

Build phases

Phase 1 makes the human workflow reliable. Phase 2 is built only when a real engagement outgrows direct reading.

Phase 1
Foundation
The human workflow made reliable.
  • Update initial-setup: guardrail v2 template, Config/ creation, numbered Summit-ordered Deliverables folders, Files On-Demand guidance, workspace-root resolution via Config/project.md.
  • Define tracker templates with the ID scheme and typed link fields; document the tracker format contract.
  • Build the intake skill: closed action set, citation format, change-set file format, processing-log updates.
  • Document the _AGENT_DRAFT lifecycle and Config approval gate in the AGENTS.md template and skill instructions.
  • Port core work skills: synthesize, conflict-check, diagram-process, compose-deliverable, manage-backlog tracker-backed, and readiness-check.
  • Port required file-format scripts; reconcile with installed skills.
  • Wire the scheduled import run: import, extract, change set, processing log, indexer stub that no-ops.
  • Tests: workspace-root resolution for nested invocation, spaces in names, missing or duplicate Config; guardrail template correctness; processing-log idempotence; tracker template validation.
Phase 2
Scale layer
Built when a real engagement outgrows direct reading.
Trigger signals — sessions re-reading the same transcripts, context budgets strained, missed cross-references, roughly 30+ sources or 100+ tracker entities.
  • Port search_index_lib.py plus the query tool; new input walkers over the workspace layout; index at ~/.ascent/<account>/<opportunity>/.
  • Lean graph builder over YAML tracker link fields; graph.json plus manifest.
  • Glossary: Config/glossary.yaml format, agent-proposed additions through the Config approval gate, query expansion.
  • Derived views: traceability audit, coverage gaps, stakeholder map, tensions — rendered as drafts or review items.
  • Turn the indexer stub live in the scheduled import run.
11

Rejected alternatives

Recorded so they are not relitigated. Expand for the reasoning.

Excel workbooks as the structured-data source of truth
Whole-file rewrite conflicts with SharePoint sync and co-authoring, and single-writer discipline is unenforceable. Trackers in markdown/YAML instead; Excel views are generated deliverables.
Root-level shared Agent Gathered/ content area
Content is engagement-specific, so the per-Opportunity Content Inbox is retained.
Porting intake_engine.py / write_registers.py / ontology machinery
Built around xlsx registers, mirror projections, mtime freshness, and git-tree assumptions that do not survive SharePoint. Concepts retained; code not.
Shared cache snapshot published to SharePoint
Workable — build locally, publish a closed artifact, consumers copy before opening — but unnecessary since builds are token-free and fast, and it adds a designated-user single point of failure.
Append-only change log with regenerated trackers
A viable growth path if tracker churn under full-copy drafts becomes painful. Not built initially.
